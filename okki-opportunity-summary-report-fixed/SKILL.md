# OKKI 商机盘点与固定格式总结报告

## 1. 本技能沉淀的沟通决策

本节是用户在本次沟通中确认的长期工作约定，后续任务应直接遵循：

1. 商机盘点覆盖全部可用商机流程，不把当前默认流程当作全量。
2. 日期口径使用商机创建时间 `create_time`，并明确时区、首尾时间和抓取时间。
3. 先取得结构化数据并核验，再写管理层结论；不编造缺失数字、金额、人员、阶段、链接或文件路径。
4. 正式报告固定参考用户提供的 OKKI 月度商机总结 HTML 版式；数据变化只更新内容，不自行换版。
5. 交付默认包括正式 HTML 和脱敏 JSON；原始 CSV、脚本、日志和草稿不作为正式文件展示。
6. 报告必须区分事实、基于字段的推断、人工确认事项和行动建议。
7. 报告中的金额、阶段、优先级、客户意向和行动建议都要带人工确认边界，不能把代理指标写成确定结论。
8. 默认只读，不创建、修改、删除OKKI商机，不修改流程、权限、绑定或系统配置。

## 2. 触发条件

以下请求都触发本技能：

- “盘点OKKI上个月/本月/本周创建的商机”
- “总结OKKI商机”“生成商机月报/商机总结报告”
- “看全部商机流程”“商机数量、金额、状态、阶段”
- “哪些商机停滞”“跟进风险”“负责人排行”“销售能力分析”
- “按上次报告格式生成”“参考这个HTML”“格式固定，不要改版”
- 用户提供商机报告 HTML、截图或样式文件并要求复用展示形式

若用户只问一个简单指标，可保留本技能的数据核验口径，但无需生成完整 HTML。

### 执行前强制步骤：角色选择（每次执行必做）

在发起任何数据查询之前，必须先通过 `ask_user` 弹框（form 单选、`allowSkip=false` 不可跳过）让用户确认本次报告的角色视角：

- **管理角色**：面向团队管理者，报告增加「人员分析」章节，聚焦团队横向对比与辅导。
- **业务角色**：面向一线业务员，报告聚焦「我的商机」个人业务视角，弱化团队对比。

角色选择结果的复用规则：

1. 执行时先检查 MEMORY.md 是否已有「商机报告角色」记录；已有则直接复用，不再弹窗。
2. 无记录时，必须弹窗选择，并把结果写入 MEMORY.md（键值如 `商机报告角色: 管理` 或 `商机报告角色: 业务`）供后续复用。
3. 用户明确要求切换视角时，重新弹窗并更新 MEMORY.md。

角色视角对报告的影响（贯穿全文）：

- **管理角色**：第五章扩充为「人员分析与团队排行」，在负责人商机数、金额基础上，增加人均商机数、人均金额、赢单率、跟进效率（有跟进记录占比、停滞占比）、横向对比与辅导建议，并标注风险/需辅导人员。
- **业务角色**：第五章改为「我的商机与我的跟进」，去掉团队横向排名与能力评分；查询时需先确认用户对应的负责人账号，按该负责人筛选商机，重点输出「我的待跟进、我的成交、我的停滞、我下一步做什么」的个人行动清单。
- 报告的元信息标签必须标注当前视角（如「视角：管理」或「视角：业务」）。

## 3. OKKI 数据查询流程

### 3.1 必须使用 OKKI 数据查询脚本

数据查询必须通过 OKKI CRM 插件的 `okki-crm-data-query` 技能和其 `scripts/cli.py` 完成，禁止手动构造查询结果、凭记忆补数据或根据旧报告推断当前数据。

典型流程：

```bash
python <OKKI_DATA_QUERY_SKILL_DIR>/scripts/cli.py create -t "明确的商机盘点问题" --timeout 120
python <OKKI_DATA_QUERY_SKILL_DIR>/scripts/cli.py poll --id <task_id> -p answer,recommend,redirect_links -f json --timeout 120
python <OKKI_DATA_QUERY_SKILL_DIR>/scripts/cli.py download --id <task_id> -o <workspace>/okki_YYYYMM_opportunities_raw --timeout 120
```

默认只获取答案、推荐问题和跳转链接；只有用户主动要求查询逻辑时才获取 `query_logic`。有 `download_url` 时，默认展示真实下载链接；只有用户主动要求下载到本地时才执行 `download`。

### 3.2 查询语句必须明确

查询语句至少写清：

- 统计周期和时区，例如 `2026-07-01 00:00:00` 至 `2026-07-15 23:59:59`，`Asia/Shanghai`
- 按创建时间 `create_time` 筛选，而不是按最近跟进时间筛选
- 全部商机流程、全部状态、全部商机范围
- 需要完整明细而非仅一个聚合数
- 需要返回流程分布、状态分布、阶段分布和金额字段
- 不修改任何数据

### 3.3 查询失败处理

- 认证失败、服务到期、权限不足、版本限制、超时或结果为空都如实说明。
- 返回“不支持该查询”时，读取 OKKI 查询技能支持范围后，最多进行 3 次有依据的查询改写；不能无限重试。
- 检测到任务涉及大批量拆分查询时，优先提示用户在 OKKI 系统内发起，避免创建大量并发任务。
- 不得以演示数据、旧数据或训练记忆替代本次查询结果。

## 4. 数据采集与解析

### 4.1 全流程覆盖

先枚举全部可用流程，至少记录流程名称和流程总数。对每个流程使用相同筛选条件：

- 创建时间：目标周期
- 商机范围：全部，例如 `show_all=1`
- 状态：全部，例如 `disable_flag=3`
- 其他筛选清空，除非用户明确指定
- 分页完整读取，确保页面总量、阶段计数和明细列表一致

不能只查询默认流程，也不能根据历史报告推断流程列表。

### 4.2 优先字段

优先获取：

- `opportunity_id`、商机编号、商机名称
- 客户/公司名称及必要的内部ID
- 流程名称
- 创建时间、创建人
- 负责人、协作人
- 币种、原始金额、USD折算金额、系统预测金额
- 当前阶段、状态
- 最近跟进时间、跟进天数、下次跟进时间
- 输单原因、来源、备注

字段未返回时写“本次明细未返回”或“系统数据为空”，不得用其他字段替代。

### 4.3 CSV 空行与汇总行

处理 OKKI 下载 CSV 时：

1. 先跳过文件开头和结尾的空行，再解析字段名。
2. 区分有明确创建时间的商机明细和创建时间为“未知”的流程/阶段汇总行。
3. 用户指定日期盘点只纳入 `create_time` 明确落在目标周期内的记录。
4. “未知创建时间”行不能自行归入目标日期，必须在数据质量和人工确认清单中披露。

## 5. 去重、核验与防幻觉

### 5.1 去重规则

优先使用唯一 `opportunity_id` 去重。接口未返回 `opportunity_id` 时，明确披露缺口并使用商机编号作为临时去重键；不得把临时键说成系统唯一ID。

交付前核对：

- 流程数量总和与返回记录数
- 返回记录数、有效日期样本数、唯一记录数、重复记录数
- 所有 `create_time` 是否在目标范围
- 各流程、阶段和状态计数与明细长度
- 状态分布合计是否等于唯一商机总数
- 原始金额、USD折算面值、系统预测金额是否分别直接来自明细
- 页面总计或抽样流程是否与接口结果一致

### 5.2 事实、推断、建议分开

- 事实：只写本轮 OKKI 工具结果、当前读取文件或用户提供内容可回链的内容。
- 推断：使用“据字段推断”“代理指标”“可能”等限定词，并写明依据。
- 建议：使用“建议”“待人工确认”，不能把建议写成系统事实。
- 没有来源的数字、比例、排名、原因、链接、路径和精度不输出。
- 测试流程、测试客户、负金额、零金额、异常大额、占位日期先标记疑似，不直接清理或剔除。

### 5.3 敏感信息处理

正式报告和 JSON 不得包含：密码、Cookie、Token、验证码、完整邮箱、完整凭据、客户内部ID、流程ID、AliID、查询任务ID、系统路径或内部 API 信息。

- 邮箱局部脱敏，例如 `m***@example.com`。
- 疑似内部标识从公司名、备注等业务字段中移除，并保留“原始字段含疑似内部标识，已脱敏，待人工确认”的说明。
- 协作人、备注中若含密码样式文本，必须清除或脱敏。
- 测试记录可以保留业务分析所需的最小名称，但须标记“疑似测试记录”。
- 不修改 OKKI 原始数据，只处理本地交付副本。

## 6. 分析口径

### 6.1 核心指标

至少输出：

- 唯一商机总数
- 流程总数、有创建记录流程数、无创建记录流程数；无法确认时写明原因
- 进行中、赢单、输单及其他状态数量
- 原币种金额合计
- OKKI USD折算面值合计
- 系统预测金额；若未返回或全部为0，照实说明
- 红色、黄色、绿色跟进风险数量和人工确认数量

面值金额和预测金额必须分开，不能合并成一个“总金额”。

### 6.2 跟进停滞

以抓取时点和最近跟进时间或系统返回的跟进天数为依据：

- `>14天`：红色，48小时内业务员+主管双触达
- `7—14天`：黄色，本周完成有效触达
- `≤7天`：绿色，保持节奏
- 最近跟进为占位值、跟进天数异常或字段缺失：人工确认，不纳入可验证分层

该指标只代表最近跟进记录的时间间隔，不等于客户一定未回复。已结束商机是否纳入必须在报告中说明。

### 6.3 负责人分析

必须区分：

- 创建人：商机进入系统的来源/建档责任
- 负责人：当前推进责任
- 协作人：参与推进的成员

负责人排行只能综合负责人商机数、阶段深度、赢单/输单、最近跟进和可见推进信号。没有完整日志时，不输出精确推进率、因果结论或能力分数。1—3条样本只能写“小样本结果亮眼/成功案例观察”。

角色视角差异：管理角色在本节基础上扩充「人员分析」——增加人均指标、赢单率、跟进效率的横向对比与辅导建议；业务角色本节降级为「我的商机」个人视角，不做全员横向排名，查询需先按当前负责人账号筛选。

## 7. 固定 HTML 报告格式

### 7.1 固定视觉系统

除非用户明确要求改版，以下内容不可改变：

- `body` 浅灰蓝背景；报告设左侧固定目录栏（宽约 230px、全屏高、垂直排列目录项、当前章节高亮、栏内独立滚动），主内容区整体右移（`margin-left` 约 230px）与目录互不遮挡；移动端（≤768px）目录回退为顶部横排、内容区恢复全宽。
- 目录栏由 JS 扫描各章节 `h2` 标题自动生成目录项（与章节一一对应、永不漏项），点击走原生锚点 `href="#secN"` + `html{scroll-behavior:smooth}` 平滑滚动，跳转不依赖 JS 事件；右下角设「回到顶部」悬浮按钮（滚动超过约 400px 出现）。
- 顶部横幅：圆角、深蓝到亮蓝渐变，参考 `linear-gradient(135deg, #12233f 0%, #1d4ed8 100%)`；白色大标题、浅蓝副标题、3枚以上圆角元信息标签（含「视角：管理/业务」）；标题可保留 `📊`。
- 横幅之后紧接黄色人工确认提示框，橙色左边框，说明金额、阶段、优先级、客户意向和行动建议需人工确认。
- 每章使用白底、浅色边框、圆角和轻阴影；章节标题深蓝并带底部细线；每章 `card` 带唯一 `id`（`secN`）供目录锚点跳转。
- 颜色含义固定：蓝色=信息/主指标，绿色=赢单/正常，黄色=本周处理，红色=立即处理，橙色=数据风险，紫色=补充指标。
- 字体优先 `Microsoft YaHei`, `PingFang SC`, `Arial`, sans-serif；不引入外部字体、图片、CSS 或脚本 URL；金额统一千分位格式。
- 表格响应式横向滚动；表头浅灰蓝；合计行浅蓝底和粗体；风险与状态用圆角 badge。
- 图表使用自包含 HTML/CSS/SVG，不依赖外部图表库：状态环形图（`conic-gradient` 展示进行中/赢单/输单占比）、流程分布条形图、负责人商机数条形图；图表与明细由同一份 JS 数据源驱动，保证一致。
- 明细表（附录）顶部设筛选器：搜索框（商机名/客户名）+ 状态/流程/负责人下拉 + 重置，筛选后实时显示「显示 N/总数 条 · 合计金额」。
- 明细表商机名链接到 OKKI 商机详情（`crm.xiaoman.cn/business/detail?id=...`，来自接口返回的商机ID）；顶部与流程表提供「在 OKKI 查看全部商机」列表跳转；客户名、手机号、内部ID等一律脱敏后才可展示。

### 7.2 固定十章节顺序

必须严格按以下顺序，编号和含义不变：

1. **一、管理层结论**：蓝底“🔎 一句话结论”和“🚨 管理层重点”列表。
2. **二、核心指标看板**：固定4列（移动端2列）响应式指标网格，展示商机总数、进行中、已赢单、已输单、最近跟进>14天、7—14天、≤7天、原币金额。
3. **三、数据可视化**：状态环形图 + 流程分布条形图 + 负责人商机数条形图（自包含，与明细同源）。
4. **四、按商机流程分布**：流程、数量、原币金额、管理提示；主表隐藏0条流程，并在说明框交代全量流程与0条流程；附商机列表跳转。
5. **五、状态与阶段概况**：左右双栏，状态分布表和阶段表；附黄色阶段口径提示。
6. **六、业务能力分析与人员排行**（按角色分叉）：管理角色为「人员分析与团队排行」——评价口径、创建人与负责人区分、负责人排行、人均商机数/人均金额、赢单率与跟进效率横向对比、辅导建议与能力判断边界；业务角色为「我的商机与我的跟进」——去掉团队对比与能力评分，只保留个人待跟进/成交/停滞与下一步行动清单。
7. **七、跟进停滞预警**：红/黄/绿预警 + 无跟进记录人工确认项，固定规则为>14天、7—14天、≤7天；说明停滞指标边界。
8. **八、金额与数据质量风险**：左右双栏，金额口径与异常数据；面值和预测严格分开，异常项列入人工确认。
9. **九、跟进建议与执行计划**：红色“48小时内”、黄色“本周”、绿色“本月完成”三个执行卡片。
10. **十、建议的商机管理规则**：固定红/黄/绿/蓝四张规则卡，说明停滞督办、周内推进、正常触达、跟进记录字段。
11. **十一、文字总结与最终建议**：完整文字总结、蓝色最终建议框和人工确认清单。

十一章之后统一保留 footer：报告生成日期、数据来源、人工复核提示。最后追加“附：商机明细”响应式表格（顶部带筛选器、点击商机名跳转 OKKI 商机详情），不改变前十一章顺序。

### 7.3 报告表达规则

- 先结论后证据，每节先给数字和判断，再解释。
- 关键数字和比例必须能回链到 OKKI 查询结果或脱敏 JSON。
- 页面标题、元信息标签必须显示统计周期、数据范围、盘点口径、角色视角和抓取时间或来源。
- 0条流程不放在流程主表，但必须在说明框或口径提示中交代。
- 阶段跨流程归并时必须写“阶段名称体系不完全一致，需人工复核”。
- 不把内部 API、Cookie、Token、流程ID、客户ID、交付目录路径放进管理层正文。
- HTML 必须自包含，可离线打开；目录、图表、筛选、跳转均为纯 HTML/CSS/原生 JS，不依赖外部库或网络。
- 业务角色与管理角色共用同一套版式（左侧目录、图表、筛选、跳转、章节结构），仅第五章内容分叉，不得因角色不同而降级版式。

## 8. 默认文件交付

正式交付默认包含：

1. `OKKI_YYYY年MM月商机总结报告_固定格式最终版.html`
2. `okki_YYYYMM_opportunities.json`

HTML 是管理层正式文件；JSON 是脱敏结构化审计附件。不要把原始 CSV、脚本、日志、草稿称为最终文件。

写入后必须验证：

- 文件存在
- HTML 可读取
- JSON 可解析
- HTML 与 JSON 的关键数字一致
- 无完整邮箱、凭据、内部ID、任务ID或系统路径

## 9. 最终交付门禁
